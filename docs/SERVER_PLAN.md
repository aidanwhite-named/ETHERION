# 서버로 옮길 때 — 점검 메모 (v3.20.1 기준)

지금은 계정 · 보유 카드 · 덱 · 지갑 · 교역소 재고가 모두 이 브라우저의 localStorage(`etherion.v3`)에 있다.
나중에는 서버가 이것들의 **정본**을 갖고, 게임은 로그인한 뒤 서버에서 받아 보여 주기만 한다.
로컬 데이터가 저절로 서버로 올라가지는 않는다(옮기려면 업로드 기능을 따로 만든다. 개발 중이면 새로 시작하는 편이 보통).

결론: **지금 서버 코드를 짤 필요는 없다.** 저장 창구가 이미 한 곳(`Store`)에 모여 있어서, 서버를 정할 때 그 안쪽을 서버 요청으로 바꾸면 된다.
아래는 그때 손볼 곳과 놓치기 쉬운 곳이다.

## 1. 이미 잘 되어 있는 것

- **창구가 한 곳.** 계정 · 컬렉션 · 덱 · 초안은 `Store`(`js/store.js`), 지갑 · 교역소 사고팔기 · 재고는 `Store` 확장(`js/economy.js`), 경험치는 `Store.addXp`(`js/level.js`). 돈은 모두 `addGold`를 거치고 기록(`u.ledger`)이 남는다.
- **데이터가 단순.** 덱은 `{카드ID: 장수}` JSON — 그대로 서버와 주고받을 수 있다.
- **설정은 따로.** 소리 · 화면 설정(`etherion.pref.*`), 크로니클 읽은 곳, 카일란 발견, 전투 로그는 계정 저장소와 따로라 로컬에 남겨도 된다(계정을 따라다니게 하고 싶은 것만 골라 서버로).
- **엔진이 화면 없이 돈다**(`cfg.headless`, 균형 도구가 쓰는 방식). 서버가 같은 엔진으로 판을 다시 굴려 결과를 확인할 수 있다(5장).

## 2. 보상을 기기가 정하는 곳 → 서버가 정해야 한다

지금은 기기에서 `Math.random`으로 뽑아 바로 준다. 서버 시대에는 기기는 "돌려 주세요"라고 요청만 하고 결과는 서버가 알려 준다.

| 곳 | 무엇 |
|---|---|
| `js/screens.js` `onMatchEnd` | 승리 보상 카드 1장 추첨 · 승패 기록 · 수레바퀴 표 +1 |
| `js/expedition.js` `Exp.onEnd` · `Exp.choose` | 원정 보상 후보 3장 · 고른 카드 지급 · 완주 보너스 |
| `js/economy.js` `pachinkoRoll` (`js/pachinko.js`, `js/minigames.js`가 부름) | 수레바퀴 · 전장 작은 게임 당첨 |
| `js/economy.js` `econBreak` · `econSettle` | 부서진 카드 2% · 승리/패배 정산 |

## 3. Store를 거치지 않고 데이터를 바로 고치는 곳

서버로 바꿀 때 놓치기 쉽다. 미리 `Store` 함수(예: `Store.recordMatch` · `Store.useSpin` · `Store.setExpedition`)로 감싸 두면 "서버로 바꿀 곳 = Store 안쪽"이 온전히 맞는다.

- `js/screens.js` `onMatchEnd` — `u.stats.w/l++`, `u.spins++`
- `js/pachinko.js` `spin` — `u.spins--`
- `js/expedition.js` — `u.expedition`을 통째로 만들고 고침
- `js/screens.js` 덱 조정실 — `delete u.fresh[id]`(새 카드 표시)
- `js/screens.js` 관리자 보관소 — 모험가의 `collection`을 바로 채움

## 4. 서버를 정할 때 바꾸는 것

- **즉시 응답 → 기다리는 방식(비동기).** 지금 `Store.buyCard`는 결과를 바로 돌려준다. 서버는 응답을 기다려야 하므로 부르는 곳을 `await`으로 바꾼다. 부르는 곳이 적다: 구매 `js/shop.js` `shopBuy`, 판매 `shopSell`, 덱 저장 `js/screens.js`(덱 조정실 저장 단추), 로그인 · 등록 · 손님(`js/screens.js` 입장 화면).
- **통째로 저장 → 행동 단위 요청.** `Store.save()`는 데이터 전체를 한 덩어리로 쓴다. 서버에는 "이 카드 1장 구매"처럼 행동만 보내고, 서버가 지갑 · 장수 · 재고를 검사한 뒤 반영한다. 덩어리째 올리게 하면 조각 · 카드를 고쳐 올릴 수 있다.
- **인증.** 지금은 암호가 평문으로 저장되고 관리자 암호(`ADMIN_PW`)가 코드에 있다. 서버 인증(암호는 서버에서 해시)으로 바꾸고, 관리자 판별도 서버가 한다.
- **교역소 재고.** 지금은 브라우저마다 따로(`Store.data.stock`). 서버에서는 모든 사람이 하나의 재고를 나눠 쓴다 — 두 사람이 마지막 1장을 동시에 사는 경우를 서버가 처리한다.
- **채팅.** `ChatNet`(`js/store.js`)에 이미 WebSocket 자리가 비어 있다(`connect` · `send` · `receive`).

## 5. 온라인 대전

지금은 PeerJS(WebRTC)로 두 기기가 바로 이어지고, 같은 시드로 각자 판을 계산하며 둔 수만 주고받는다(`js/online.js`). 친선전으로는 그대로 좋다.
보상이 걸린 대전(랭크 등)이 되면 각 기기가 결과를 정하는 구조라 조작할 수 있다. 그때는:

- 서버가 짝을 지어 주고(매칭), 판의 시드를 서버가 정한다.
- 판이 끝나면 서버가 **시드 + 양쪽이 둔 수 기록**을 받아 headless 엔진으로 다시 굴려 승패를 확인한 뒤 보상을 준다.
- 이렇게 되려면 지금 규칙이 계속 지켜져야 한다: 판의 결과를 바꾸는 난수는 `GRand()` · `shuffleG()`만, 사람이 둘 수 있는 행동은 모두 `ACT_FNS`(AGENTS.md "온라인 대전").

## 6. 순서 제안

1. (지금, 작게) 3장의 직접 수정하는 곳을 Store 함수로 감싸기 · 2장의 보상 추첨을 `Store.roll…` 같은 창구로 모으기.
2. (서버를 정할 때) 서버 API 설계: 로그인 · 내 데이터 받기 · 덱 저장 · 사기/팔기 · 판 결과 보고 · 보상 받기.
3. `Store` 안쪽을 서버 요청으로, 부르는 곳을 비동기로.
4. 온라인 대전 검증(5장)은 보상이 걸린 대전을 열 때.
